# 决策模型辅助测试研究（Bivia）

日期：2026-11-09。范围：`忘了没` Android 项目的测试辅助，不涉及业务代码修改。

> 结论先行：Bivia 在“给定证据做原子事实判断/证据分级”上表现好，在“对一条完整声明下最终裁决”“失败根因分类”“测试范围多选”上表现差且会高置信度出错。建议把它当**事实抽取器**，不要当**测试裁决器**。

## 1. 方法

- SDK：`bivia==1.0.0`，隔离 venv `.venv-bivia/`。
- 输入只包含测试名、失败摘要、最小代码片段、现有测试名；不发送密钥、`local.properties`、签名或用户数据。
- 所有判断都由 Bivia API 返回；本文只做输入构造、结果汇总和人工标注对照。
- 人工标注来自 `docs/bug-report-code-review-2026-11-07.md`、`docs/03-acceptance.md` 和现有测试。
- 原始结果在 `test-results/bivia/`（已被 git 忽略，不进入发布证据）。

## 2. 结果总览

| 任务 | 问法 | 样本 | 匹配 | 观察 |
|---|---|---|---|---|
| 失败分诊 | 五分类 choice | 2 | 1/2 | flaky 用例被判“选择器/数据错误”，置信度 0.98/1.00；环境类判对 |
| 失败分诊 deep | 五分类 choice | 2 | 0/2 | 两条都 `readout_disagreement` 弃权 |
| 缺陷声明裁决 | 成立/误报/证据不足 | 3 | 0/3 | 三条全判“成立”；#2、#3 是人工确认的误报 |
| 缺陷声明裁决 + 判定规则 | 同上 | 3 | 0/3 | 仍全判“成立”，置信度 0.63～0.95 |

| 产品缺陷门控（规范性） | boolean：“是否需要修复” | 3 | 2/3 | 两条测试失败判 no 正确；已知数据丢失限制判 no，与人工 yes 不符 |

| 验收证据分级 | 四分类 choice | 7 | 6/7 | 唯一不一致是 AC25“未覆盖” vs “已实现但证据不足”，本身语义有歧义 |
| AC25 + 判定口径 | 四分类 choice | 1 | 0/1 | 仍选“已实现但证据不足”，置信度 0.99 |
| 原子代码事实 | 三选一 choice | 3 | 3/3 | 检查顺序、锁内 epoch 校验、refresh 先 remove 再 render 全部答对 |

## 3. 关键发现

### 3.1 问题形状比模型模式更重要

同一批代码：

- 问“这条缺陷声明是否成立？”→ 0/3，且高置信度错误。
- 问“这段代码先检查还是先加法？”→ 3/3。

说明 Bivia 能读取并比较代码中的局部事实，但在“完整声明 + 最终裁决”的问法下会顺着声明走。`deep` 只能让部分样本弃权，不能纠正错误。

**用法含义**：不要让 Bivia 对一条复合声明做最终判断；先把声明拆成 3～5 个原子事实问题，再按规则汇总。

### 3.2 事实性问法优于规范性问法

- “这次失败是否由产品代码缺陷导致？”→ 2/2 正确。
- “这条已知限制是否属于需要修复的产品缺陷？”→ 判 no，与人工 yes 不符。
- “该限制是否存在用户输入丢失的可能性？”→ 判 yes，正确。

规范性判断依赖“应该修什么”的立场，模型没有项目上下文；事实性判断只依赖可观察证据，表现稳定。

### 3.3 验收证据分级是目前最可用的场景

7 条 AC 中 6 条与人工一致，包括：

- 已覆盖且有证据（AC01、AC26）
- 已实现但证据不足（AC18、AC21、AC27）
- 不适用（负一屏）

唯一不一致的 AC25 是“未覆盖”与“已实现但证据不足”的边界；补了判定口径后模型仍选后者。这个场景可以作为**发版前的辅助盘点**，但输出必须由人确认，不能直接写进 `docs/evidence/`。

### 3.4 测试范围多选不可靠

- 小部件改动：完全匹配。
- 更新下载改动：多选了“设备 instrumentation”和“真机设备矩阵”。
- 纯文档改动：Bivia 返回“不选任何项”，没有选“仅文档审阅”。

`multi_select` 的概率也不适合直接当门槛：纯文档案例中“更新/安装手工验证”概率 0.80，但人工判断完全不相关。测试范围应由路径到测试集的确定性规则表决定，Bivia 最多回答“这个文件是否影响 Android 运行时行为”这类原子事实。

### 3.5 高置信度不是安全信号

错误样本中出现过：

- flaky 失败分诊：1.00 判“选择器/数据错误”
- 缺陷声明 #2：0.95 判“成立”
- 缺陷声明 #3：1.00 判“成立”
- AC25：0.99 判“已实现但证据不足”

正确样本中原子事实和事实性门控也常见 0.92～1.00。结论：置信度只在**同一任务类型内**有参考价值，不能跨任务当自动采纳门槛；更不能因为 ≥0.8 就跳过人工。

### 3.6 SDK 边界问题

`multi_select` 在没有选中任何选项时返回 `value=None`，Python SDK 反序列化 `SetDecision` 会抛：

```text
ValidationError: SetDecision.value Input should be a valid list, input_value=None
```

本项目工具已把这种情况记为 `[]` 并保留 `sdk_error`，但这属于 SDK 缺陷，接入生产前应向厂商确认或固定版本。

## 4. 推荐的辅助测试架构

```text
测试产物 / 缺陷声明 / 代码片段
        │
        ▼
人工或模板拆成原子问题（3～5 个，二选一/三选一）
        │
        ▼
Bivia API（choice/boolean，带最小证据和判定口径）
        │
        ▼
确定性规则汇总（任一事实反驳 → 否定；全部支持 → 支持；缺失/弃权 → 人工）
        │
        ▼
人工确认 → 写入 test-results/bivia/（不写 docs/evidence/）
```

### 适用

- 验收证据等级分级（辅助盘点，6/7）
- 代码原子事实提取（3/3）
- 事实性 boolean 门控（3/3）
- “这条日志是否包含产品异常堆栈”“这次改动是否触及 Android 运行时”等低分支问题

### 不适用

- 缺陷声明的最终裁决（0/3，且高置信度错误）
- 失败根因五分类（0/1，flaky 误判）
- 测试范围 multi_select（1/3）
- “是否应该修复”这类规范性判断（0/1）
- 任何 pass/fail、自动改代码、自动合并

## 5. 下一步实验

1. **缺陷复核流水线**：实现 `verify_claim.py`，输入“声明 + 原子事实规格”，调用 Bivia 取事实，再用规则输出“成立/误报/证据不足”。先在 10 条历史声明上评测。
2. **验收证据审计**：把 AC01～AC27 全部跑一遍，和 `docs/03-acceptance.md` 的人工结论对照；目标 ≥80%，并单独统计高置信度错误。
3. **失败分诊改造**：放弃五分类，改成 3 个事实性 boolean（是否有产品异常堆栈、同代码重跑是否通过、失败是否发生在测试框架启动前）+ 确定性行动表；用 20 条历史失败验证。
4. **测试范围规则化**：建立“改动路径 → 测试集”规则表；Bivia 只回答“是否影响 Android 运行时行为”这类原子问题。
5. **评测集**：每个任务至少 30 条人工标注，记录准确率、弃权率、高置信度错误数；未达标不接入发版流程。

## 6. 复现命令

```bash
python -m venv .venv-bivia
source .venv-bivia/Scripts/activate
pip install -r scripts/bivia/requirements.txt
export A8_API_KEY="..."

# 原子事实
python scripts/bivia/run_cases.py \
  --input scripts/bivia/cases/bug-claims/atomic-facts.json \
  --out test-results/bivia/atomic-facts

# 验收证据分级
python scripts/bivia/run_cases.py \
  --input scripts/bivia/cases/eval/round2.json \
  --out test-results/bivia/round2
```

所有输出均为 advisory，不是测试证据。
